# External assurance runs against the post-implementation Subject

Mission Start freezes each selected Assurance Provider's exact identity and prepares a durable Invocation, but it does not call the Provider against the repository baseline. The engineering Runner first completes the Developer Role, publishes implementation Evidence, and asks the Kernel to freeze a path-free Attempt Assurance Subject. Provider execution is legal only after that Subject exists. This keeps external assessment bound to the code that will reach the Quality Gate while preserving atomic Host Policy selection at Mission acceptance.

A fulfilled, transport-valid Assurance Submission remains a Provider claim. The Runner re-reads the imported Evidence copy and applies the provider-neutral V1 eligibility profile for Provider Composition, Provider Policy, Coverage, Source Seal, Provenance, and Evidence. It submits only eligibility facts to the Kernel. The Kernel derives the Machine Provider Assurance Assessment and Assurance Result, and the Quality Gate consumes only those Results: failed requires Rework, indeterminate blocks, and satisfied discharges only the named external requirement.

Rework never reuses external assurance credit. The Kernel preserves prior Attempt history, copies its frozen Provider obligations into the next Attempt, prepares new Invocation identities, and requires a new post-implementation Subject, Submission, Assessment, and Result. A missing, unavailable, rejected, unreadable, or incomplete Provider therefore cannot disappear from a later Gate decision or silently degrade to approval.
